# Caribbean Trade — Этапы 1–6 (экономика + торговля + ASCII-интерфейс + ручное управление + AI-торговцы + события мира)

Рабочий прототип экономической стратегии на **Godot 4.x + GDScript** по
техническому плану v0.1.

- **Этап 1 — экономическое ядро.** Пять городов симулируются 365 дней без
  графики: производство, потребление, цены, население. Деньги сохраняются
  точно, запасы ограничены, цены реагируют на дефицит и избыток.
- **Этап 2 — торговля и логистика.** У игрока есть бригантин на круговом
  маршруте (Тортуга → Гибара → Порт-Рояль → Кайман). Корабль покупает дёшево
  там, где товар в избытке, и продаёт дорого там, где его не хватает — и
  приносит проверяемую прибыль.
- **Этап 3 — карта и интерфейс.** ASCII-карта в духе Dwarf Fortress: пять
  городов по координатам, корабль ползёт по сетке, маршрут — пунктиром. Справа
  панель выбранного города (рынок: товар/запас/цена/спрос/предложение), панель
  корабля (трюм/кошелёк/маршрут), лог событий и кнопки скорости (пауза/1×/2×/3×).
  Ни одного PNG или спрайта — всё рисуется кодом в `_draw()` и `Label`.
- **Этап 4 — ручное управление.** Корабль игрока больше не авто-торгует: в порту
  он швартуется, симуляция авто-паузится, игрок покупает/продаёт кнопками и
  редактирует маршрут (`Up/Dn/Del`, `+Add`), затем жмёт «Отплыть».
- **Этап 5 — автономный мир (AI-торговцы).** Помимо игрока в мире работают три
  AI-компании со своими кораблями и маршрутами. Они торгуют через те же
  `MarketSystem`/`TradeSystem`, что и игрок, двигают цены и забирают долю
  арбитража — мир больше не ждёт игрока. Деньги по-прежнему сохраняются точно.
- **Этап 6 — события мира.** Штормы, засухи и голод как временные модификаторы:
  шторм замедляет корабль и пробивает дыру в бюджете (доп-upkeep в местный
  порт), засуха режет урожай, голод вспыхивает там, где кончается хлеб. События
  катаются на отдельном сиде (детерминизм) и идут через те же счета — деньги
  сохраняются и при 160 событиях за год.

> Главный принцип архитектуры: **симуляция не зависит от интерфейса.** Если
> убрать всю графику, города, предприятия, цены, корабли и маршруты продолжают
> работать. Этот проект — тому доказательство.

## 1. Установка Godot

1. Скачайте **Godot 4.x (Standard, не .NET)** с
   [godotengine.org/download](https://godotengine.org/download).
2. Распакуйте архив — это один бинарник, без зависимостей и без установки.
3. Запустите `Godot`, нажмите **Import**, выберите файл `project.godot` в этой
   папке. Проект откроется в редакторе.

Godot 4.3 или 4.4 — оба подходят. .NET-версия не нужна: весь код на GDScript.

## 2. Как запустить симуляцию

### Из редактора (визуально — ASCII-интерфейс Этапов 3–4)
Откройте проект → **F5**. Сцена `main.tscn` открывает окно: слева ASCII-карта,
справа панели. Симуляция идёт **непрерывно**, без жёсткой остановки на 365 дней.
Скорость — кнопками **Pause / 1× / 2× / 3×** или клавишами `1` `2` `3`, `Space`
пауза. Клик по городу на карте выбирает его — справа виден его рынок
(запас/цена/спрос/предложение). Панель корабля показывает трюм, кошелёк и
маршрут (`>` у текущей остановки), лог снизу пишет сделки и приходы в порт.
**ESC — выход.**

Карта — моноширинный шрифт: `T P C G S` — города (Тортуга/Порт-Рояль/Кайман/
Гибара/Сантьяго), `b` — бригантин в море, `B` — в порту, `·` — маршрут.
Шрифт берётся из `ui/fonts/DejaVuSansMono.ttf` (если редактор его импортировал)
либо из системного mono через `SystemFont` — поэтому работает и прямым запуском
`godot --path .`, без открытия редактора.

### Безголовый режим (верификация Этапов 1–2, без UI)
```bash
godot --headless --path /путь/к/caribbean_trade
```
Пробегает 365 дней, печатает в консоль сохранение денег и прибыль игрока,
пишет `sim_summary.txt` / `sim_daily.csv` / `company_money.csv` в
`user://sim_output/` (абсолютный путь напечатан в конце) и выходит. Окна и
карты в этом режиме нет — это та же верификация, что и в Этапах 1–2.

### Тесты
```bash
godot --headless --path /путь/к/caribbean_trade tests/test_market.tscn        # Этап 1
godot --headless --path /путь/к/caribbean_trade tests/test_trade.tscn         # Этап 2
godot --headless --path /путь/к/caribbean_trade tests/test_manual_trade.tscn  # Этап 4
godot --headless --path /путь/к/caribbean_trade tests/test_ai_traders.tscn    # Этап 5
godot --headless --path /путь/к/caribbean_trade tests/test_events.tscn        # Этап 6
```
`test_market` проверяет: цена растёт при дефиците и падает при избытке;
покупка ограничена запасом и деньгами; производство невозможно без сырья.
`test_trade` проверяет: корабль не может продать товар, которого у него нет;
круговой маршрут приносит прибыль за 60 дней; деньги при этом сохраняются.
`test_manual_trade` проверяет: ручная покупка двигает деньги и запас; продажа
ограничена трюмом; покупка — трюмом и кошельком; roundtrip сохраняет деньги.
`test_ai_traders` проверяет: AI-компании спавнятся с кораблём/маршрутом/
auto_trade; торгуют через общий рынок; деньги сохраняются; цены двигаются;
карта рисует все корабли (игрок + 3 AI).
`test_events` проверяет: события детерминированы (два прогона — один счётчик);
деньги сохраняются при включённых событиях; засуха режет урожай вдвое; голод
вспыхивает по дефициту запаса, а не по броску кубика.
GUT не обязателен — сцена сама печатает PASS/FAIL и выходит с кодом 0/1.
Всего **20 проверок (5+2+5+4+4)**.

### Поменять сид (мир меняется)
В `core/world_state.gd` строка `var world_seed: int = 1337`. Поменяйте число —
население городов пересчитается по формуле `sin(seed + ...)`, спрос/цены/прибыль
изменятся, но деньги всё равно сохраняются (drift = 0). Примеры прогонов на
разных seed — в разделе 7.

## 4. Что уже проверено (эталонная прогонка на Python)

Эталонная реализация на Python (`scripts/econ_ref.py` вне этого проекта)
повторяет формулы GDScript один-в-один и прогоняет те же 365 дней. Результат
прогонки (seed = 1337):

**Этап 1 — экономика:**
- **Сохранение денег: start = 133 600, end = 133 600, drift = 0.0000.** Ни одна
  монета не создаётся и не исчезает. `population_money + market.fund + Σ
  industry.money + Σ company.money` постоянно.
- **Удовлетворённость 0.70–0.92** во всех пяти городах, население медленно
  растёт (не коллапсирует).
- **Цены реагируют на дефицит и избыток:** кукуруза в избытке → цена у дна
  (≈3); хлеб при лёгком дефиците → 54; товары, которые город не производит
  (ткани, ром в ряде городов) → цена у потолка. Это и есть сигналы для торговли.
- **Запасы ограничены:** сырьё с перепроизводством упирается в glut-кап
  (`stock > 2.5 × target` → предприятие встаёт), бесконечных накоплений нет.

**Этап 2 — торговля:**
- **Маршрут прибыльный:** игрок 5 000 → 67 291 за 365 дней (прибыль +62 291).
  Это эталон Этапа 2 (один корабль, без AI-торговцев); с Этапа 5 в мире четыре
  корабля и прибыль игрока ниже — +52 262 (см. блок Этапа 5 выше). Траектория
  растёт плавно (~170/день), не одной удачной сделкой.
- **Деньги по-прежнему сохраняются** с включённым игроком: drift = 0.0000.
  Прибыль игрока — это реальный арбитраж (деньги перетекают между рынками
  городов через корабль), а не созданные из воздуха деньги.
- **Тесты проходят:** корабль не продаёт товар, которого нет в трюме; маршрут
  даёт +11 252 за 60 дней при drift = 0.0000 (теперь с AI-торговцами в мире).

Критерии Этапов 1 и 2 из плана v0.1 выполнены.

**Этап 5 — автономный мир (AI-торговцы), seed = 1337:**
- **Сохранение денег: start = 144 100, end = 144 100, drift = 0.0000** — уже с
  четырьмя кораблями (игрок + 3 AI). AI платит upkeep и торгует через те же
  `MarketSystem`/`TradeSystem`, что и игрок, поэтому инвариант не нарушается.
- **Прибыль игрока упала: 5 000 → 57 262 (+52 262)** против +62 291 без AI.
  Это и есть доказательство, что мир стал конкурентным: AI-компании забирают
  часть арбитража, который раньше целиком доставался игроку.
- **Все три AI-компании прибыльны за год:** Havana Sugar +38 680, Santiago
  Metals +19 556, Carib Produce +22 540 (стартовые 3 500 у каждой). Они реально
  двигают цены: сахар в Гибаре 50→5 (перепроизводство + выкуп AI), металл в
  Порт-Рояле 83→242 (дефицит + спрос кузницы).
- **Тесты проходят:** 16/16 (5+2+5+4), включая `test_ai_traders` (спавн,
  торговля через общий рынок, сохранение денег, движение цен, карта рисует
  все корабли).

**Этап 6 — события мира, seed = 1337:**
- **Сохранение денег при 160 событиях:** drift = 0.0000 (start = end = 144 100).
  Штормы, засухи и голод идут только через существующие счета (доп-upkeep
  корабля → местный город; панические покупки населения → market.fund; засуха
  просто режет урожай) — ни одного созданного или уничтоженного дуката.
- **160 событий за год:** drought=26, storm=36, famine=98, 4 ещё активны на
  финише. Прибыль игрока упала до +42 857 (с +52 262 на Этапе 5) — штормы

- **Голод — следствие симуляции, не бросок кубика:** вспыхивает, когда запас
  хлеба/кукурузы в городе < 0.5×target (концепт §3.4). Поэтому города без

- **Тесты проходят:** 20/20 (5+2+5+4+4), включая `test_events` (детерминизм

## 6. Как устроена экономика (кратко)

**Деньги.** У каждого города три счёта: `population_money` (кошелёк жителей),
`market.fund` (буфер рынка, может уходить в минус — это кредит производителям)
и `money` у каждого предприятия. Любая сделка двигает реальные деньги через
`market.fund`: покупка платит рынку, продажа забирает у рынка. Сумма
сохраняется.

**Цена.** `price = base · exp(elasticity · (target − stock)/target)`,
зажатая в `[min, max]`. `target = max(7, demand·7)` — буфер на неделю спроса.
Дефицит → цена растёт, избыток → падает.

**Производство.** Предприятие планирует число партий `= min(мощность,
affordable)` и запускается **только если** (а) выход не в glut
(`stock > 2.5·target`) и (б) выручка за партию ≥ себестоимости. Без сырья
выпуск 0. Выход продаётся на рынок по текущей цене.

**Потребление.** Три класса (бедные/средние/богатые) со своими корзинами.
Покупка идёт в порядке приоритета (хлеб и кукуруза первыми), каждый товар
ограничен запасом и остатком кошелька — поэтому отсутствие рома не голодит
город. Удовлетворённость = куплено / нужно.

**Население (раз в неделю).** Удовлетворённость > 0.8 → рост, < 0.5 → упадок.
Предприятия нанимают/увольняют по недельной прибыли, рынок труда ограничивает
занятость. **Дивиденды:** прибыль предприятий выше резерва возвращается
населению — без этого сырьевые предприятия копят деньги, а город голодает.

**Внешняя торговля** в `MarketSystem` есть, но **выключена**. Импорт и экспорт
между городами — это работа кораблей игрока (Этап 2). Поэтому деньги
сохраняются точно, а товары, которые город не производит, остаются в дефиците
с высокой ценой — это и есть указатель, куда везти груз.

**Торговля (Этап 2).** Корабль имеет трюм (`cargo` + `cargo_used`/`cargo_capacity`),
скорость и дневной upkeep. Каждый день: upkeep платится из `company.money` и
уходит в население порта (деньги остаются в обороте); корабль плывёт к
остановке; по прибытии исполняет правила маршрута и уходит к следующей
остановке — по кругу.

Каждое правило `StopRule` — это `(good, action, threshold, max_qty, price_limit)`:
- **buy**: покупать, пока запас в порту выше `threshold` (сливает избыток),
  по цене не выше `price_limit`, сколько влезло в трюм и хватило денег;
- **sell**: продавать, пока запас в порту ниже `threshold` (ломает дефицит),
  по цене не ниже `price_limit`, сколько есть в трюме.

Правила **самоограничивающиеся**: корабль не заливает рынок под ноль, а
останавливается, когда арбитраж исчерпан (запас дошёл до threshold). Все
сделки идут через `MarketSystem.buy/sell` — деньги движутся
`company.money ↔ market.fund`, груз — в трюм/из трюма. Корабль не может
продать товар, которого у него нет (`execute_sell` проверяет трюм первым).
Маршрут игрока по умолчанию берёт ром/сахар/табак в Гибаре и Тортуге (где их
производят дёшево) и продаёт в Порт-Рояле и Каймане (где их нет и цена у
потолка).

## 7. Детерминизм

Симуляция детерминирована при фиксированном seed: фиксированный порядок
операций в дневном тике (экономика города → корабли → часы), никаких случайных
чисел в Этапах 1–2. Два прогона с одним seed и одними данными дают одинаковый
CSV. Это основа для автотестов и балансировки.

**Seed меняет мир.** В `core/world_state.gd` стоит `var world_seed: int = 1337`.
При постройке мира население каждого города (poor / middle / rich) умножается на
`1 + 0.2·sin(seed + town_idx·7 + class_offset)` — возмущение деньго-нейтрально
(население не входит в `total_money()`, так что сохранение денег не нарушается),
но меняет структуру спроса → цены → арбитраж → прибыль. Разные seed дают разные
результаты при drift = 0:

| seed | прибыль игрока за 365 дней | drift | события |
|---|---|---|---|
| 1337 (по умолчанию) | +42 857 | 0.0000 | 160 |
| 42   | +45 116 | 0.0000 | 116 |
| 9999 | +48 839 | 0.0000 | 141 |
| 7    | +45 720 | 0.0000 | 154 |

Формула `sin()` (а не ГПСЧ Godot) выбрана сознательно — эталонная Python-реализация
воспроизводит её бит-в-бит тем же seed. Прибыль ниже, чем на Этапе 2 (+62 291 при
seed 1337): сначала (Этап 5) её забирают AI-торговцы, потом (Этап 6) её давят
штормы и засухи. События катаются на отдельном ГПСЧ (`event_rng`) и в `sin()`-формулу
населения не лезут — поэтому seed→население по-прежнему бит-в-бит, а счётчик событий
тоже воспроизводим (см. тест `events_deterministic`).

## 8. Этап 3 готов — что внутри

Этапы 1–3 готовы. Экономика устойчива, корабль торгует с прибылью, деньги
сохраняются, а поверх всего этого — ASCII-интерфейс без единого ассета. **Этап 4
(ручная торговля + редактор маршрута + авто-пауза в порту) достроен поверх —
см. секцию 9.** Ниже описан baseline Этапа 3; секция 9 перечисляет, что именно
добавилось и изменилось.

**Архитектура UI.** Симуляция по-прежнему не знает об интерфейсе: системы
экономики и кораблей только **эмитят** сигналы в `EventBus`, а UI только
**слушает** и читает `WorldState`/`SimulationClock`. Обратные вызовы из UI в
симуляцию — только управление скоростью тика и (с Этапа 4) команды игрока
(`player_buy`, `depart_ship`, `route_*`) через тонкий контроллер `main.gd`;
UI никогда не трогает `Market.Entry.stock` напрямую.

- `ui/ascii_map.gd` (`class_name AsciiMap`, `extends Control`) — карта. Сетка
  60×30 моноширинных символов; мир `(x∈[100,540], y∈[160,400])` линейно
  отображается на неё. Маршрут рисуется пунктиром по Брезенхэму между
  остановками, города — буквами `T P C G S`, корабль — `b` (в море) или `B`
  (в порту). Перерисовка раз в день по `EventBus.day_advanced`. Клик по символу
  города выбирает его (сигнал `town_selected`).
- `ui/game_ui.gd` (`extends Control`) — правая колонка: кнопки скорости,
  день/неделя, кошелёк, панель рынка выбранного города, панель корабля с
  маршрутом, лог последних 16 событий. Обновляется по `day_advanced`,
  `town_updated`, `trade_completed`, `message`.
- `main.gd` — тонкий контроллер. Windowed: строит мир, создаёт `GameUi` и
  крутит непрерывный тик с управляемой скоростью (0/4/16/60 дней в секунду).
  Headless: те же 365 дней + CSV/отчёт (верификация Этапов 1–2 не изменилась).

**Сигналы `EventBus` теперь все активны:** `day_advanced`, `week_advanced`,
`town_updated`, `trade_completed`, `ship_docked`, `message` шлются системами;
UI на них реагирует. `price_changed` объявлен, но пока не эмитется —
`town_updated` полностью покрывает нужды панели рынка; он зарезервирован для
спарклайнов (Этап 7+).

**Шрифт.** Карте нужна моноширинность. `ui/fonts/DejaVuSansMono.ttf`
подгружается через `load()` (если редактор импортировал ассет), а иначе
`SystemFont` берёт системный моно-шрифт — поэтому проект запускается и прямым
`godot --path .`, без открытия редактора.

## 9. Этап 4 готов — что внутри

Этап 4 превращает зрителя в капитана. Корабль больше не торгует и не уходит
сам: в windowed-режиме у него `auto_trade == false`, поэтому по прибытии в
порт он швартуется и **ждёт игрока**. Симуляция при этом авто-паузится, чтобы
можно спокойно поторговать и спланировать следующий переход. Headless-
верификация (365 дней) не изменилась — там `auto_trade` остался `true`,
маршрут крутится сам, деньги по-прежнему сохраняются.

**Игровой цикл.** Старт: корабль стоит на Tortuga, симуляция на паузе, открыта
торговая панель Tortuga.

1. **Торговля в порту.** Пока корабль в порту `_selected_town`, панель города
   показывает на каждый товар строку `good · stock · price · hold` и кнопки
   `Buy 1 / Buy 10 / Sell 1 / Sell 10 / All`. Кнопки вызывают
   `main.player_buy` / `player_sell`, которые идут через
   `TradeSystem.manual_buy` / `manual_sell` — те же `MarketSystem.buy` / `sell`,
   что и у авто-маршрута, но без правил-порогов: фиксированное количество по
   текущей цене дня. Три жёстких лимита: свободный трюм, остаток на складе
   города, деньги в кошельке. Деньги идут `company ↔ market.fund` — инвариант
   сохранения денег не нарушается (проверено тестом `roundtrip_conserves_money`).
2. **Редактор маршрута.** Панель «Route»: на каждую остановку строка
   `Up / Dn · ▶ Town · Del` (порядок, удаление), внизу кнопка `+ Add <выбранный
   город>` (добавляет город, по которому кликнули на карте). Маршрут
   обновляется на лету — `TradeRoute.stops` те же поля, что и из
   `data/routes.json`.
3. **Отплытие.** Кнопка `Depart → <след. город>` ставит `state="sailing"`,
   назначает следующую остановку (`TradeRoute.next_stop_after`), снимает паузу
   (скорость 1×). Корабль плывёт, на прибытии `ShipsTick` эмитит
   `EventBus.ship_docked` → `main._on_ship_docked` снова ставит паузу и
   открывает панель нового порта. Цикл замыкается.

**Цена фиксирована на день.** `manual_buy` / `manual_sell` берут `current_price`,
пересчитанный в конце предыдущего дня (`MarketSystem.update_market`). Цена в
течение одной стоянки не двигается от ваших сделок — она обновится на следующий
день. Это сознательное упрощение (так же работает авто-маршрут в Этапах 2–3);
мгновенное изменение цены от объёма сделки — задача Этапа 7 (баланс).

**Что изменилось в коде:**

- `core/event_bus.gd` — новый сигнал `ship_docked(ship_id, town_id)`.
- `entities/ship.gd` — флаг `auto_trade: bool` (true по умолчанию; windowed
  ставит false у корабля игрока).
- `simulation/ships_tick.gd` — на прибытии эмитит `ship_docked`; docked-блок
  (авто-торговля + авто-отплытие) выполняется **только** при `auto_trade`,
  иначе корабль просто стоит в порту.
- `simulation/systems/trade_system.gd` — `manual_buy` / `manual_sell`
  (фиксированное количество, лимиты по трюму/складу/кошельку, деньги
  `company ↔ market.fund`).
- `main.gd` — windowed: `auto_trade=false`, старт на паузе на Tortuga,
  `ship_docked` → авто-пауза + выбор порта; методы `player_buy`, `player_sell`,
  `depart_ship`, `route_add`, `route_remove`, `route_move`,
  `player_dock_town_id`, `player_next_destination`. Headless — без изменений.
- `ui/game_ui.gd` — торговая панель (кнопки на товар) вместо текстовой таблицы,
  когда корабль в выбранном порту; редактор маршрута (`Up/Dn/Del`, `+Add`);
  кнопка `Depart`. Подписка на `ship_docked` добавилась.
- `tests/test_manual_trade.gd` + `.tscn` — 5 проверок.

**Тест `tests/test_manual_trade.tscn`** (5/5 PASS):
`manual_buy_moves_money_and_stock`, `manual_sell_capped_by_cargo`,
`buy_capped_by_cargo_space`, `buy_capped_by_money`, `roundtrip_conserves_money`.

### Что дальше (Этап 7+)

1. **Миссии и цели** — доставка груза к сроку, накопление капитала, победа /
   поражение; панель «Цели».
2. **POPs и рынок труда** (из концепта §4) — превратить poor/middle/rich в
   реальные группы с профессиями, сбережениями, уровнем жизни и миграцией.
3. **Пираты и войны** (концепт §3.4) — блокады портов, пиратские кампании,
   войны государств как более тяжёлые системные события поверх Этапа 6.
4. **Баланс и полировка** (Этап 7): тонкая настройка производства/потребления,
   цен кораблей, частоты событий, мгновенное изменение цены от объёма сделки.

   часто (в городах без своего зерна) — по мере роста флота и тонкой настройки
   `trigger_stock_ratio` оба закроются.

## 10. Этап 5 готов — что внутри

Этап 5 делает то, ради чего проект задуман (концепт §17): **мир начинает жить
сам**. Помимо игрока в нём работают три AI-торговые компании, каждая со своим
кораблём и маршрутом. Они не получают ни денег, ни товаров из воздуха — ходят
через те же `MarketSystem`/`TradeSystem`, что и игрок, платят upkeep и
конкурируют за арбитраж. Игрок из единственного торговца стал одним из четырёх.

**Дата-драйвен.** AI-компании описаны в `data/ai_companies.json` (имя, стартовый
капитал, тип корабля, маршрут, домашний порт), их маршруты — в `data/routes.json`
рядом с маршрутом игрока. Спавн детерминирован (никакого ГПСЧ), поэтому
воспроизводимость и сохранение денег не страдают.

Три AI-маршрута построены как реальный арбитраж — купить сырьё там, где его
производят (цена в избытке падает), продать там, где потребляют (цена в дефиците
растёт):
- **Havana Sugar Co.** (Гибара → Тортуга → Порт-Рояль): сахар и табак из Гибары,
  сахар в Тортугу (на местную винокурню), табак в Порт-Рояль.
- **Santiago Metals** (Сантьяго → Порт-Рояль): металл и металлоизделия из
  Сантьяго (шахта + кузница) в Порт-Рояль (кузница потребляет металл, богатые
  покупают изделия).
- **Carib Produce** (Кайман → Порт-Рояль → Гибара): фрукты из Каймана (сад) в
  города-потребители, обратно сахар из Гибары.

Каждое правило — тот же `StopRule (good, action, threshold, max_qty,
price_limit)`, что и у игрока: AI не заливает рынок под ноль, а останавливается,
когда арбитраж исчерпан (запас дошёл до threshold).

**Что изменилось в коде:**
- `data/ai_companies.json` (новый) + три маршрута в `data/routes.json`.
- `core/world_state.gd` — спавн AI-компаний/кораблей (`auto_trade=true`,
  домашний порт) после игрока; хелперы `get_ship(id)` и `get_player_ship()`
  (корабль игрока ищется по `owner_id=="player"`, а не по индексу `ships[0]`).
- `main.gd` — авто-пауза **только** на док игрока (`_on_ship_docked` проверяет
  `ship_id`); headless-отчёт теперь печатает каждую AI-компанию (деньги, P/L,
  net_trade); `get_player_ship()` вместо `ships[0]`.
- `ui/ascii_map.gd` — рисует **все** корабли: AI `a`/`A` (циан), игрок `b`/`B`
  (красный) поверх; маршрут пунктиром — только игрока (чтобы не загромождать).
- `ui/game_ui.gd` — `get_player_ship()` вместо `ships[0]`; `_on_ship_docked`
  обновляет панели только для игрока (AI-доки подхватываются дневным
  `day_advanced`, иначе каждая стоянка конкурента перерисовывала бы панель).
- `tests/test_ai_traders.gd` + `.tscn` — 4 проверки.

**Тест `tests/test_ai_traders.tscn`** (4/4 PASS): `ai_companies_spawn` (3 AI,
у каждой корабль+маршрут+auto_trade+домашний порт, игрок идентифицируем),
`ai_trades_and_conserves_30d` (AI реально торгует, drift=0.0000, цены ушли от
базы: сахар 50→5, металл 83→242), `player_and_ai_share_market_14d` (и игрок, и
AI торгуют через общий рынок, drift=0), `map_draws_all_ships` (на сетке есть
`B` игрока и ≥3 `A` конкурентов).

## 11. Этап 6 готов — что внутри

Этап 6 добавляет **события мира** (концепт §3.4): временные модификаторы,
которые накладываются поверх экономики, не ломая ни conservation, ни
детерминизм. События катаются на **отдельном ГПСЧ** (`WorldState.event_rng`,
сидится от `world_seed`), а голод вообще без броска — он чисто
state-triggered. Три архетипа:

- **Засуха** (drought, на город) — режет урожай crop-индустрий в `magnitude`
  раз (`production_system._capacity_batches` умножает на
  `WorldState.drought_multiplier`). Сырьё дорожает, переработка (ром, хлеб)
  голодает уже по входу. Денег не трогает.
- **Шторм** (storm, на корабль) — скорость `×magnitude` и доп-upkeep
  (`extra_upkeep_mult × upkeep_daily`) на ремонт, который уходит в местный
  порт: `company.money → town.population_money`. Корабль медленнее и дороже.
- **Голод** (famine, на город+товар) — вспыхивает сам, когда запас хлеба или
  кукурузы в городе падает ниже `trigger_stock_ratio × target`. Поднимает
  спрос населения в `magnitude` раз → паническая скупка → price spike. Это и
  есть «следствие симуляции» из концепта.

**Дата-драйвен.** `data/events.json` описывает все три архетипа (magnitude,
длительность, вероятность, триггеры). `simulation/systems/world/event_system.gd`
хранит активные `ActiveEvent` в `WorldState.active_events`, раз в неделю
крутит новые (`roll_weekly`), раз в день снижает `days_left` и удаляет
истёкшие (`decay_daily`).

**Что изменилось в коде:**
- `data/events.json` (новый) + `simulation/systems/world/event_system.gd` (новый).
- `core/world_state.gd` — `active_events`, отдельный `event_rng`, `events_db`,
  query-методы (`drought_multiplier`, `storm_multiplier`, `storm_extra_upkeep`,
  `famine_demand_multiplier`); `reset()` теперь сбрасывает и `SimulationClock`
  (иначе второй `build_world` в одном процессе ломал выравнивание недели —
  эту ловушку поймал тест `events_deterministic`).
- `production_system.gd` — засуха режет capacity crop-индустрий (`CROP_GOODS`).
- `ships_tick.gd` — шторм множит скорость и добавляет доп-upkeep.
- `consumption_system.gd` — голод множит спрос (и в demand-сигнале, и в
  фактической покупке).
- `simulation_engine.gd` — `EventSystem` в `_init`, `decay_daily` в конце
  `step_day`, `roll_weekly` в `step_week` (после экономических тиков, чтобы
  голод видел недельный запас).
- `main.gd` — события в headless-отчёте и в summary-файле.
- `tests/test_events.gd` + `.tscn` — 4 проверки.

**Тест `tests/test_events.tscn`** (4/4 PASS): `events_deterministic` (два
прогона из `build_world` дают одинаковый счётчик событий — 11=11),
`events_conserve_money_60d` (drift=0.0000 при 25 событиях),
`drought_cuts_crop_output` (кукурузная ферма Гибары 32 → 16, ratio 0.50),
`famine_triggered_by_shortage` (хлеб в ноль в Гибаре → голод на (gibara,bread)
без единого броска).

## 12. GDScript для питониста — шпаргалка

| Python | GDScript |
|---|---|
| отступы 4 пробела | отступы **Tab** (обязательно) |
| `def foo(a: int) -> str:` | `func foo(a: int) -> String:` |
| `None` / `True` / `False` | `null` / `true` / `false` |
| `import` | `preload("res://...")` или `class_name` |
| `dataclass` | `class_name Foo extends RefCounted` + `_init()` |
| `json.load` | `JSON.parse_string(text)` |
| открытие файла | `FileAccess.open(path, FileAccess.READ)` |
| `f"{x:.2f}"` | `"%.2f" % x` |
| `"...".format(a=x)` / f-string с несколькими | `"%.2f %.2f" % [x, y]` — **массив `[...]`, не кортеж `(...)`** |
| `b = a > 3` | `var b: bool = a > 3` (явный тип; `:=` не выводит тип у bool-выражений) |
| сигналов нет | `signal x(v)` + `x.emit(v)` / `x.connect(...)` |

Все ресурсы — в `res://` (read-only в экспорте), сохранения — в `user://`.
Автозагрузка (`autoload` в `project.godot`) — это глобальный синглтон:
`WorldState`, `SimulationClock`, `EventBus` доступны из любого скрипта по имени.

## 15. Дизайн-заметки

README содержит spec-уровень
(что мы хотим). Этот раздел — дизайн-заметки по реализации того, что ещё не
построено, и фиксация архитектурных решений, которые нельзя описать на
уровне spec.

### 15.1. Приоритеты аудита vs существующий roadmap

Аудит предлагает свою очерёдность (P1 → P2 → P3 → later). Мы **не заменяем**
существующий roadmap A–F, а используем как дизайн-линзу — причины в README
(блок перед roadmap). Краткое отображение:

- Audit P1 (labour market, chains, resources, warehouses, enterprises) ↔
  B2 (существующий) + C6/C7/C8/C9 (новые) + G (новый раздел).
- Audit P2 (migration, companies, credit, info, budgets) ↔ B (migration уже
  в spec), Stage 5 done, C3+C4 (существующие), AIBrain `PriceMemory`
  (частично), A4 (существующий).
- Audit P3 (crises, monopolies, instability, smuggling, epidemics) ↔
  I (новый раздел) + B6/B7 (новые в B).
- Audit later (tech, privateers, autonomy, regional markets) ↔
  K (новый), D1, J (новый).

С фаворитом аудита («предприятия + рынок труда + производственные цепочки»)
полностью согласны — это и есть C1 + C8 + B2 + C7, связывающее ядро. Эти три
механики способны связать население, рынок, торговлю, финансы и государство
в одну систему; многие другие механики строятся поверх уже существующей
экономики, а не придумываются для каждой отдельная логика.

### 15.2. Дизайн-заметки по ключевым механикам

**Производственные цепочки как DAG.** Сейчас `data/recipes.json` — плоский
список: каждый рецепт сразу берёт сырьё и даёт готовый товар (sugar → rum,
cotton → textiles, metal → metal_goods). Цель — ввести промежуточные товары
и сделать цепочки многоуровневыми:

- `sugar_cane` (сырьё, новый) → `sugar` (рецепт: 2 sugar_cane) → `rum`
  (рецепт: 2 sugar) — сейчас `sugar` ведёт себя как сырьё, но исторически
  это продукт переработки тростника;
- `iron_ore` (сырьё, новый) → `metal` (рецепт: 2 ore + fuel) → `metal_goods`
  (рецепт: 2 metal);
- `wood` → `lumber` (рецепт: 2 wood) → используется в `shipyard` (новое
  предприятие);
- `cotton` → `cloth` (промежуточный) → `clothing` (готовый) — вместо
  нынешнего `textiles`.

Архитектурно это **не** новый класс — это просто больше записей в
`recipes.json` + новые goods в `goods.json`. Дефицит распространяется
автоматически, потому что `production_system.gd::_capacity_batches` уже
проверяет доступность входов перед запуском партии: нет sugar_cane → нет
sugar → нет рома. Единственная нетривиальная правка — визуализация цепочки в
UI (дерево зависимостей товара).

**Побочные продукты.** Добавить в схему рецептов опциональное поле
`byproducts`. Примеры: лесозаготовка даёт `wood` + `resin` (побочно);
перегонка рома даёт `rum` + `molasses`; кузница даёт `metal_goods` +
`slag` (отход, в идеале не товар, а «загрязнение» — см. ниже). Побочные
продукты **не** определяют решение о запуске партии, но появляются на рынке
как доп. предложение. Это банально ~10 строк в `production_system.gd`
(дополнительный цикл по `byproducts` рядом с основным output) и одно новое
поле в `recipes.json`. Для отходов-загрязнений (не товаров) — отдельное
поле `waste`, влияющее на `Town.pollution` (см. G1).

**Земля и ресурсы.** Добавить в `Town` блок `resources`:

```
{fertility: 0..1, wood_reserve: int, water: int,
 mineral_deposits: {metal: int, ...}, suitable_crops: [sugar_cane, cotton, ...]}
```

Истощение: каждый такт производства `lumber_camp` уменьшает `wood_reserve`
на выход партии; при `wood_reserve < threshold` мощность падает, при 0 —
остановка. Восстановление: `wood_reserve += regrowth_rate * dt` (медленно,
десятилетиями). Плодородие уменьшается при непрерывной эксплуатации одной
культуры, восстанавливается при севообороте или залежи. Это **не** новая
система — это данные в `towns.json` + небольшие хуки в `production_system`
(проверять reserve перед партией) и один новый weekly-тик
(`resources_system.gd` для regrowth). Связь с C7: истощение `wood_reserve`
автоматически рвёт цепочку `wood → lumber → shipyard`, поэтому кризисы
верфи — это следствие ресурсной модели, а не отдельной системы.

**Склады.** Сейчас `Market.stock` — это и торговый запас, и стратегический
запас предприятия (всё в одном словаре). Их нужно разделить:

- `Market.stock` — краткосрочный торговый запас, то что доступно для
  покупки/продажи в данный день;
- `Town.warehouse` (новый) — долгосрочное хранение, с полями
  `{capacity, entries: {good: {qty, spoilage_rate, value}}}`.

Перемещение между складом и рынком — отдельная операция (для игрока — кнопка
«положить на склад / выложить на рынок»; для AI — решение в `AIBrain` на
основе `price_memory` и сезонных ожиданий). Порча: раз в день
`qty -= spoilage_rate * qty` для скоропортящихся товаров (fruits, bread,
fish). Это явное расширение `Town` + один новый класс `Warehouse` (или
просто подсистема в `town.gd`) + UI блок. **Связь с G2 (сезонность)**:
склады имеют смысл, когда есть что складывать на сезон — без G2 это просто
долгое хранение, без стратегии.

**Рынок труда с конкуренцией.** Сейчас `population_system.gd` нанимает и
увольняет по недельной прибыли предприятия, ограничиваясь занятостью в
городе (`employed` vs `available_workers`). Цель — добавить квалификации
(`Pop.qualification = [farmer, smith, sailor, ...]`) и конкуренцию: несколько
предприятий в одном городе могут одновременно хотеть одного и того же smith;
зарплата растёт, пока либо предложение не покроет спрос, либо предприятие не
откажется от найма. Архитектурно — новый `EmploymentSystem` (или расширение
`population_system.gd`) раз в неделю пересчитывает рынок труда по каждому
городу: собирает demand по industries, сравнивает с available_by_qualification,
мэтчит с wage adjustment. Связь с C1: пока нет `owner_id`, невозможно
решать, кто именно нанимает (предприятие игрока vs AI) — поэтому B2 в
зависимостях идёт после C1.

**Эпидемии через торговую сеть.** Добавить `Town.infection` поле
(per-disease dict). Распространение: корабль, прибывший в инфицированный
порт, получает `infection` с вероятностью proportional to `Town.infection`
level; по прибытии в следующий порт — может передать дальше (портовые
quarantine mechanics могут это блокировать — отдельный state policy).
Внутри порта infection растёт по logistic curve, влияет на `available_workers`
(снижает) и `consumption` (снижает — больные не ходят на рынок). Это
полностью поверх существующих `Ship`/`Town` + новый `EpidemicSystem` раз в
день. **Связь с H4 (info asymmetry)**: слухи об эпидемии в порту могут быть
ложными или устаревшими — торговец принимает решение обходить порт на основе
своей памяти, а не реального состояния.

**Эндогенные кризисы как стресс-тест, не event.** Цепочка аудита (неурожай
→ рост цен → падение доходов → ...) должна **собираться** из уже существующих
механик, а не срабатывать по триггеру. Чтобы убедиться в этом, добавим
stress-test сценарий в `tests/`: руками зануляем `wood_reserve` в одном
регионе и смотрим, как дефицит досок рвётся по цепочке → корабли дорожают →
торговля меняется → города голодают. Если цепочка обрывается на 2-м шаге
(например, shipyard не зависит от lumber, потому что строит из абстрактного
`wood`) — значит, нужно усилить связь, а не вводить кризис-событие.
Архитектурно — это **не новая система**, это набор wire-up'ов между
существующими (production → prices → consumption → unrest → state budget),
плюс stress-test как валидация.

**Репутация как вектор.** Сейчас у игрока есть `reputation` со state и с
пиратами (Stage A1+A2 + Diplomacy panel). Аудит предлагает расширить:
репутация с торговцами, банкирами, страховщиками — отдельные оси. Это
позволяет моделировать «торговец с плохой репутацией у банков, но хорошей у
пиратских гаваней» — очень в духе эпохи. Архитектурно —
`Company.reputation: Dict[String, float]` вместо одного скаляра; UI Diplomacy
panel расширяется до нескольких строк. Не ломает существующих тестов,
потому что они проверяют `reputation[state_id]` через хелпер, который
остаётся совместимым.

**Информационная асимметрия.** Основа есть — у каждой AI-компании есть
`PriceMemory` с меткой устаревания (`stale > 10d`). Развитие:

- `PriceMemory` хранит не только цены, но и «уверенность»
  (`confidence = 1 / (1 + days_since)`);
- добавить источники информации: rumours (распространяются через порты,
  иногда ложные — `expected = real * (1 + noise)`), official bulletins
  (платные, точные — покупка за `cost = base * confidence`), personal
  network (по друзьям/партнёрам — бесплатно, но покрывает только свои
  города);
- игрок видит только свою `PriceMemory`, не чужую — UI должен это
  подчёркивать (например, серая цена «по слухам» vs зелёная «по личному
  посещению»).

Два торговца с разной информацией принимают разные решения на том же
рынке — это и есть асимметрия. Архитектурно — это **расширение** `PriceMemory`
+ `AIBrain`, не новая система.

**Антимонопольная механика.** Если одна компания контролирует > X% предложения
товара в городе (считается через новое поле `Market.supply_share[good] =
{company_id: share}`), государство может: (а) ввести антимонопольную пошлину,
(б) разорвать контракт, (в) наоборот — дать привилегию (если у компании
хорошая репутация). Выбор — за state policy AI (связь с A4). Архитектурно —
`Market.supply_share` обновляется в `MarketSystem.sell`, раз в неделю
`state_policy_system.gd` (новый) проверяет пороги и применяет решения.

**Контрабанда как альтернативный граф.** **НЕ** копия легальной торговли с
`tax=0`, а отдельная подсистема:

- свои точки (contraband markets в пиратских гаванях и corrupt ports);
- свои цены (выше легальных на импорт, ниже на экспорт — это маржа за риск);
- свои риски (конфискация при customs check, репутационные потери у
  государств, `reputation[pirates]` рост);
- свои посредники (fences — отдельный NPC класс или подсеть компаний).

Архитектурно — параллельный `ContrabandMarket` (отдельный класс, не
расширение `Market`) + точки входа через `Ship` при наличии флага
`can_smuggle`. Связь с A4 (customs) и I5 (reputation vector): конфискация
бьёт по репутации с государством, повышает с пиратами.

### 15.3. Где мы не согласны с аудитом

- **«Дерево технологий — нет»** — частично согласны для эмерджентного мира
  (AI не исследует tech tree), но для player agency минимальное дерево
  технологий нужно (игрок должен видеть прогресс). Решение (см. J4): для AI
  технологий нет, для игрока есть упрощённое (3-4 ступени на направление, не
  классическое Paradox-дерево).
- **«Полноценная политика — после рынка труда»** — согласны полностью,
  поэтому B2+B5 в roadmap идут раньше B7 (unrest) и I1 (crises).
- **«Не реализовывать все механики как отдельные подсистемы»** — согласны
  концептуально (главное — причинно-следственная связность), но
  архитектурно всё-таки сохраняем разделение на `systems/` (по одному файлу
  на систему) ради тестирования и читаемости; причинно-следственная
  связность достигается через общее состояние в `WorldState`, а не через
  слияние систем в один файл. Тесты (`tests/`) проверяют именно что связи
  между системами работают, а не только каждую систему в изоляции.
- **«Каперы как приоритет later»** — согласны: каперы (K3) требуют военной
  логистики (K1) и state treasury расходов (A4), без них это будет просто
  пиратство с лицензией. Поэтому K3 идёт после K1.
- **Audit's P-ordering vs existing A–F** — см. README блок перед roadmap:
  не заменяем A–F, расширяем. Audit не учитывает content (D), gameplay (E),
  visual (F) — а без них проекта нет, это просто симулятор без игры.

## 16. C1 (minimal) — собственность предприятий и routing дивидендов

C1 minimal — первое внедрение audit-favourite «предприятия + рынок труда +
производственные цепочки». В этом срезе **только** ownership и routing
дивидендов; покупка/продажа/строительство — отдельный срез C2.

### 16.1. Что добавлено

- **`Industry.owner_id: String`** (`entities/industry.gd`). Формат:
  `"town:<id>"` (дефолт, сохраняет Stage 1–6 поведение), `"player"`,
  `"ai:<co_id>"`, `"state:<sid>"`, `"entrepreneur:<id>"`. Пустая строка
  fallback к town. Опциональный 6-й параметр `_init` — существующие 5-arg
  вызовы (`test_market.gd:85`, `world_state.gd:142`) не ломаются.
- **`default_owner` stub** в `data/industries.json` для всех 12 шаблонов
  (`"town"`). Поле парсится в `world_state.gd:140`; `"town"` резолвится в
  `"town:<town_id>"` в момент инстанциации; другие значения pass-through.
  Верхний уровень JSON содержит `_default_owner_doc` — строка-документация
  назначения поля (безопасна: `industries_db` lookup'ится только по ключам
  из `town.industries`, и `_default_owner_doc` там нет). Заглушка явно
  оставлена для будущего C2/C8, где шаблоны смогут стартовать с другим
  владельцем (например, `"ai:havana_sugar"` для sugar plantation).
- **`FinanceSystem._route_dividend(t, ind, payout)`** — новый private метод
  в `simulation/systems/finance_system.gd`. Заменил прямое
  `t.population_money += payout` в `distribute_profits`. Routing:
  - `""` / `"town:*"` → `t.population_money` (baseline)
  - `"player"` → `WorldState.get_company("player").money`
  - `"ai:<co_id>"` → `WorldState.get_company(co_id).money`
  - `"state:<sid>"` → `WorldState.get_state(sid).treasury`
  - `"entrepreneur:*"` → fallback к `t.population_money` (entrepreneur
    entity не смоделирован — реальный routing приедет с позже)
  - anything else → fallback к `t.population_money` (safe default)

  Использует `WorldState` autoload напрямую — так уже делают
  `production_system`, `consumption_system`, `trade_system`, `war_system`,
  `ai_brain` (grep'ом проверено).
- **`world_state.gd:135-147`** — чтение `default_owner` из шаблона и
  резолв `"town"` → `"town:<town_id>"` в момент создания Industry.
- **`tests/test_ownership.gd` + `.tscn`** — 3 новых теста:
  `dividend_routes_to_town_by_default` (baseline сохранился), 
  `dividend_routes_to_player_when_owned` (player получает payout, drift=0),
  `unknown_owner_falls_back_to_population` (entrepreneur fallback, drift=0).

### 16.2. Почему conservation сохранился

`WorldState.total_money()` уже суммирует `companies[i].money`,
`states[i].treasury`, `towns[i].population_money`, `towns[i].treasury`,
`towns[i].market.fund`, `towns[i].industries[j].money`. Routing дивиденда
переносит `payout` из `industry.money` в один из этих счётов — каждый
целевой счёт в сумме, поэтому drift=0 в каждой ветке.

Верификация: `test_dividend_routes_to_player_when_owned` и
`test_unknown_owner_falls_back_to_population` оба проверяют `drift < 0.001`
через `WorldState.total_money()` before/after `distribute_profits`. 365-day
headless sim: `start=528700.0 end=528700.0 drift=0.0000`, player profit
+13619.3 (совпадает с baseline до C1 — поведение не изменилось, потому что
все industries в `build_world` получают `owner_id="town:<id>"`).

### 16.4. Что НЕ сделано в этом срезе (явно)

- **Buy/sell industries** — нет UI, нет API `player_buy_industry`. Это C2.
- **Build new industries** — нет. Это C2.
- **`book_value` field** — нет. Появится в C2 когда нужна будет цена

- **`capacity_level`, `wear`, `expansion_cost`** — нет. Это C8.
- **`entrepreneur` entity** — нет. `owner_id="entrepreneur:*"` fallback к

- **UI** — нет UI для ownership; в `game_ui.gd` панель industries не
  показывает owner_id. Это C2 — вместе с buy/sell UI.

### 16.5. Зачем нужен `default_owner` stub в JSON сейчас

Поле добавлено как заглушка с явным TODO-объяснением
(`_default_owner_doc` в верхнем уровне JSON + комментарий в
`world_state.gd:135-139`). Причины:

1. **Data explicit.** Когда в C2/C8 добавится entrepreneur/AI-владения,
   шаблон уже сможет указать `"default_owner": "ai:havana_sugar"` — без
   правок кода, только данных.
2. **Code-data contract.** Парсинг `default_owner` уже написан и
   протестирован косвенно (через `test_dividend_routes_to_town_by_default`
   + 365-day sim с owner_id="town:*"). Когда придёт C2, не нужно будет
   трогать `world_state.gd` — только JSON.
3. **Stub без функциональности — safe.** Все 12 шаблонов сейчас
   `"town"`, что эквивалентно старому поведению (повседневные операции
   не трогают owner_id, только `distribute_profits` его читает).
