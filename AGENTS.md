# Среда выполнения Godot 4.7.2 (Linux Sandbox)

Проект написан на чистом GDScript и использует Godot 4.7.2. Работа выполняется в облачной Linux-песочнице без графического экрана. Все операции с Godot необходимо выполнять в headless-режиме.

## 1. Подготовка среды

Перед запуском любых проверок выполни:

```bash
bash setup_godot.sh
```

Скрипт скачивает подготовленный бинарный файл Godot 4.7.2 из релизов этого репозитория.

- Не устанавливай Godot через `apt-get`.
- Не скачивай альтернативные версии движка из интернета.
- Используй только `./.godot_bin/godot`.

## 2. Импорт ресурсов и подготовка кэша

На свежем чекауте (`.godot/` кэша нет — он в `.gitignore`) ОДИН раз прогрей кэш class_name, иначе autoload'ы с типизированными массивами (`Array[Town]`, `Array[Company]` и т.п.) не парсятся и тесты не запускаются: `./.godot_bin/godot --headless --path . --import`. Повторять не нужно, пока не удалишь `.godot/`.

Перед первой проверкой проекта в чистой или новой песочнице обязательно выполни импорт ресурсов:

```bash
./.godot_bin/godot --headless --path . --import
```

Этот шаг подготавливает ресурсы проекта и внутренний кэш Godot (`.godot`). Без предварительного импорта результаты запуска могут зависеть от состояния кэша.

Если проект или импортируемые ресурсы изменились, повтори импорт перед проверками.

## 3. Проверка и запуск

Всегда используй `--headless` при работе с движком.

- **Проверка синтаксиса и загрузки проекта:**

```bash
./.godot_bin/godot --headless --path .
```

Не используй `godot --check-only`: этот режим может зависать в данной среде.

- **Запуск проекта с последующим завершением:**

```bash
./.godot_bin/godot --headless --path . --quit
```

- **Запуск отдельного теста:**

```bash
./.godot_bin/godot --headless --path . res://tests/test_name.tscn
```

- **Запуск полного набора тестов:**

Запускай тестовые сцены отдельно, если в проекте нет специального общего тестового запуска. Проверяй код завершения процесса и результаты `PASS` / `FAIL`. Не считай тест успешным только потому, что движок завершился без видимой ошибки.

После изменений в коде выполняй необходимые проверки. При изменении ресурсов повторно выполняй импорт.

## 4. Анализ проекта и планирование следующего этапа

Перед предложением следующего этапа:

1. Изучи актуальное состояние всего проекта, а не только недавно изменённые файлы.
2. Сверь реализованные механики с `README.md` и соответствующими разделами документации.
3. Определи, что уже реализовано полностью, что реализовано частично, а что ещё не реализовано.
4. Не предлагай повторно механики, которые уже существуют в коде.
5. Учитывай зависимости между системами и влияние новых механик на экономику, баланс, консервацию денег и детерминизм симуляции.

Сначала предложи следующий логичный этап и дождись подтверждения. Не приступай к реализации до согласования.

## 5. Согласование реализации

Поскольку системы проекта постепенно усложняются, перед реализацией каждого нового этапа необходимо:

1. Обсудить, что именно должно быть добавлено.
2. Предложить несколько разумных вариантов реализации, если они существуют.
3. Объяснить предполагаемую работу каждого варианта и его влияние на уже существующие системы.
4. Указать риски, ограничения и необходимые тесты.
5. Дождаться решения пользователя.

После подтверждения, если пользователь изменил, сократил или расширил первоначальный план, повторно оцени согласованный вариант перед началом работы.

Только после окончательного согласования приступай к реализации. Если реализация технически невозможна или противоречит архитектуре проекта, объясни причину и предложи альтернативу.

## 6. Завершение работы и доставка

После реализации:

1. Выполни необходимые проверки и тесты.
2. Проверь `git diff`, чтобы убедиться, что изменены только необходимые файлы.
3. Создай один коммит с однострочным сообщением.
4. Подготовь ZIP-архив, содержащий только изменённые и новые файлы, с сохранением исходной структуры каталогов проекта.
5. В ответе сообщи, что было сделано, какие проверки выполнены и каковы их результаты.
6. Предоставь ZIP-архив для скачивания.

Не заявляй об успешном прохождении тестов, если они фактически не запускались.
